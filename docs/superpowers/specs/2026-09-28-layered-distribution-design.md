# 分层分发与增量更新 — 设计文档

- 日期：2026-09-28
- 状态：已确认，待实现
- 起点：v1.2.0 released，main @ ebab397
- 关联：`2026-09-28-ui-refresh-and-rebrand-design.md`（本设计并入其第二期）

## 1. 背景

当前每次更新都要下载完整安装器。v1.2.0 的 full 变体安装包为 1536 MB，其构成是：

| 组成 | 大小 | 变化频率 |
|---|---|---|
| Python 运行时 + PyQt5 + OpenCV | 约 122 MB | 几乎不变（等同 lite 变体体积） |
| torch 2.5.1 + torchvision + CUDA 12.4 运行时库 + sam2 | 约 1.4 GB | 几乎不变 |
| 应用自身代码 | 约 30 KB | 每次发布都变 |

**实测结果（2026-09-28，CI run 36421966949）**：安装目录展开后共 4038.2 MB，其中应用层
81.0 MB，运行时层 3957.2 MB。压缩为安装包后，完整包 1536.2 MB，应用包 **74.9 MB**。
即代码改动的更新体积降为原来的 **1/20**。

应用层比最初估算的 20-30 MB 大，因为 exe 内嵌的 PYZ 除应用代码外还含 PyQt5、numpy 等第三方
纯 Python 代码，且 MobileSAM 的 ONNX 模型（`labeling_tool/models/sam/*.onnx`）也计入应用层。
若将来想进一步压缩，把 ONNX 模型移入运行时层是最直接的一步，代价是模型更新时需要完整重装。

也就是说，为了投送 30 KB 的代码改动，用户需要下载 1.5 GB，其中 1.4 GB 与上一版逐字节相同。

SAM2.1 模型权重不在此列：它已经是首次使用时下载到 `checkpoint/` 的，不打进安装包。1.5 GB 中没有模型权重。

## 2. 目标

把安装包拆成两层，使得只有应用代码变化时，更新只下载应用层（实测 74.9 MB，原为 1536 MB）。
运行时层变化时，退回完整安装包。

**非目标**：不追求把更新压到极致（逐文件差分、二进制 patch）。运行时层一年未必变一次，为它做增量不划算。

## 3. 已确认的决策

| 项 | 决策 | 放弃的备选与理由 |
|---|---|---|
| 实现方式 | 两个 Inno Setup 安装器（完整包 + 应用包） | 自建更新器进程做文件级替换：流量更省，但要自己处理替换失败、断电中断、回滚、权限，且绕开了已在真机验证过的安装链路。外部 zip 自解压：同样的问题，外加"exe 正在运行"的死结 |
| 运行时层更新 | 发完整安装包，用户重装一次 | 运行时层也做增量：需要完整的文件清单比对、完整性校验与回滚机制，工程量和出错面都大得多 |
| 分层方向 | 应用层用白名单，其余全归运行时层 | 运行时层用白名单：新增的第三方依赖会悄悄混进应用更新包，装上去可能缺文件 |
| `runtime` 版本来源 | CI 构建后计算运行时层文件哈希汇总 | 手工维护编号：必然有人忘记递增 |
| 分期 | 并入 UI 改版的第二期（v1.3.0） | 单独成期：与改名、变体收敛动的是同一批文件，分两次改要把同一个文件翻两遍 |

### 3.1 分期重排

用户确认当前软件**尚未分发**，只有他本人的机器安装了 v1.2.0，本次他会手动重装。因此改名导致的更新链路中断不再是顾虑，原三期计划压缩为两期：

| 期 | 内容 | 版本 | 用户动作 |
|---|---|---|---|
| 一 | 加载提示内嵌（已完成，PR #8 已合并） | — | — |
| 二 | 改名 + 图标 + 变体收敛 + **本设计** | v1.3.0 | 手动安装完整包，最后一次 |
| 三 | 标注窗口方向 B | v1.4.0 | 自动更新，只下应用层 |

原计划的 v1.2.1 取消，加载提示的修复直接包含在 v1.3.0 中。

## 4. 版本模型

`build-info.json` 增加 `runtime` 字段：

```json
{"version": "1.3.0", "runtime": "r3f8a1c92", "variant": "full", "commit": "abc1234"}
```

`runtime` 由 CI 计算，对两样东西取哈希，取前 8 位十六进制并加 `r` 前缀：

1. **`pip freeze` 的输出**（在全部依赖安装完成后采集）——即构建环境中每个包的**实际解析版本**。
2. **`packaging/labeling_tool.spec`** ——它通过 `collect_all` / `excludes` 决定哪些包进入运行时层。

不能只哈希需求文件：`requirements.txt` 并未精确固定版本（`PyQt5>=5.15`），pip 每次可能解析到不同
版本而文件毫无变化。这一点在分层场景下是致命的——PyQt5、numpy 的**纯 Python 代码随 exe 进入应用层**，
而它们的 `.pyd` 在运行时层，跨版本投送应用包等于装了半个升级，`import` 直接失败。

**这是回退方案，最初的设计是对构建产物取哈希。** 实测（2026-09-28，CI run 36421966949 与
36424404832）同一提交两次构建产出不同的 runtime id（`ra9adeaed` 与 `r138b837f`），证明
PyInstaller 的产物不可重现。若沿用产物哈希，每次发布 `runtime` 都会变，客户端永远匹配不到
应用包，分层更新形同虚设。

清单哈希精度略低——依赖内容变化但版本号未变时不会触发——但绝对稳定。它的误差方向是安全的：
任何对这四个文件的改动都会要求一次完整重装，包括与运行时无关的改动。反过来漏判才是危险的，
那会把应用包装到不兼容的运行时上。

未深究不可重现的根因：诊断需要下载并比对两个 1.5 GB 产物，而回退方案已消除该需求。若日后
值得修复，从 `SOURCE_DATE_EPOCH` 与 `PYTHONHASHSEED` 入手。

`labeling_tool/update/version.py` 的 `BuildInfo` 增加 `runtime: str | None` 字段。缺失或格式不符时读作 `None`，与现有的"读不到就是 dev 构建"策略一致。`is_release_build` 额外要求 `runtime` 非空。

## 5. 分层规则

**应用层（白名单，只有这些）**：

```
LM_LabelingTool.exe
_internal/labeling_tool/**          （含 models/sam/*.onnx）
_internal/annotation_tool/**
```

**运行时层**：其余一切。

方向不可颠倒。应用层是白名单意味着新增的任何第三方依赖都会自动落进运行时层，于是 `runtime` 哈希变化，于是自动要求完整重装 —— 这正是正确行为。反过来做，新依赖会混进应用更新包，用户装上去可能缺文件。

应用自身的纯 Python 代码由 PyInstaller 打进 PYZ 并嵌入 exe，因此绝大多数代码改动只表现为 `LM_LabelingTool.exe` 一个文件的变化。

## 6. CI 产物切分

`.github/workflows/build-windows.yml` 的构建流程：

1. `pyinstaller` 照常构建，产出 `dist/LM_LabelingTool/`
2. 按第 5 节的白名单分层，计算运行时层哈希汇总得到 `RUNTIME_ID`
3. 写入 `build-info.json`
4. Inno Setup 执行两次，用 `/DMyLayer=full` 与 `/DMyLayer=app` 切换：
   - 完整包 `LM_LabelingTool-Setup-v{版本}.exe`（整个目录）
   - 应用包 `LM_LabelingTool-App-v{版本}-{runtime}.exe`（仅应用层）
5. `SHA256SUMS.txt` 收录两个包

两个包使用同一个 `AppId`，使应用包被识别为升级而非并排安装。

`runtime` 出现在应用包文件名中是本设计的关键：资产名本身即索引，客户端无需任何额外元数据文件即可判断能否增量更新。

## 7. 客户端选包逻辑

`labeling_tool/update/checker.py` 的 `find_update()` 增加 `runtime` 参数，按三层优先级选择：

```python
app = f"LM_LabelingTool-App-v{version}-{runtime}.exe"
if app in assets and app in sums:
    return UpdateInfo(kind="app", ...)      # 运行时层未变，下载应用层
full = f"LM_LabelingTool-Setup-v{version}.exe"
if full in assets and full in sums:
    return UpdateInfo(kind="full", ...)     # 运行时层已变，下载完整包
return None                                  # 无可用资产，静默跳过
```

`UpdateInfo` 增加 `kind: str` 字段（`"app"` 或 `"full"`）。

沿用现有约束：没有已发布校验和的资产一律不安装。

## 8. 界面呈现

两种更新的提示文案不同，把代价讲清楚：

- `kind == "app"`：告知新版本号与下载大小（几 MB），确认后直接更新并重启
- `kind == "full"`：明确说明本次需要重新安装完整包（约 1.5 GB），让用户自行选择时机

下载、SHA256 校验与静默安装流程完全不变（`/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /RESTARTAPP`）。该链路已于 2026-09-28 在真机完成 v1.1.0 → v1.2.0 的验证，本设计不修改它。

应用包在 Inno Setup 的 `[Code]` 段增加一道防御性检查：安装前读取目标目录的 `build-info.json`，`runtime` 与包名不符则拒绝安装并提示下载完整包。正常路径由资产名保证不会出错，这道检查防的是用户手动下错包。

## 9. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| PyInstaller 构建不可重现（时间戳、路径写入产物），导致相同依赖两次构建的运行时层哈希不同 | 每次发布都要求完整重装，本设计失效 | **实现的第一步就验证**：同一提交连续构建两次，比对运行时层哈希。若不可重现，退回用依赖清单哈希（`requirements.txt` + `packaging/build-constraints.txt` + torch/CUDA 版本串）作为 `runtime`，精度略低但绝对稳定 |
| Inno Setup 升级安装时用应用包覆盖卸载日志，导致卸载后残留运行时层文件 | 卸载留下约 1.4 GB 垃圾 | 实测验证：装完整包 → 装应用包 → 卸载 → 检查安装目录是否清空。列为实现计划中的独立验证步骤。若确有此问题，改用 `[UninstallDelete]` 显式声明运行时层目录 |
| 资产名与客户端模板漂移 | 客户端匹配不到资产，静默不提示更新 | CI 中断言生成的两个资产名与 `checker.py` 的模板一致。第一期复审已指出此类风险，现在有两个模板，更易漂移 |
| 应用包安装后与运行时层不兼容（例如应用代码用了新版依赖的 API） | 程序启动即崩溃 | `runtime` 由 `pip freeze` 的解析结果与 `packaging/labeling_tool.spec` 共同决定：任何依赖版本变化、任何打包规则变化都会改变它，从而走完整包路径。**注意这不是绝对的**——若某依赖内容变化而版本号未变（例如同版本重新发布），`runtime` 不会移动 |

## 10. 测试

- `checker.py` 的选包逻辑做单元测试，stub 掉 GitHub API，覆盖：应用包优先、`runtime` 不匹配时退回完整包、两者都缺时返回 `None`、缺少校验和时返回 `None`。
- `version.py` 读取 `runtime` 字段的单元测试，覆盖缺失与格式异常。
- CI 中断言生成的资产名与 `checker.py` 的模板字符串一致。
- CI 的安装—自检—卸载流程扩展为：装完整包 → 自检 → 装应用包 → 自检 → 卸载 → 断言目录清空。
- 全量测试套件保持绿（当前基线 404）。
